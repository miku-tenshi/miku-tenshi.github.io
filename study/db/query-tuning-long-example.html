쿼리 튜닝 삽질기

느려터진 리포트 쿼리 하나를 붙잡고 하루 종일 씨름한 기록. 이 글은 일부러 길게 써서, 카드 안에서는 스크롤이 생기고 전체화면으로 펼치면 그 안에서만 스크롤되는 걸 확인하려고 만든 예시다.

1. 증상. 관리자 페이지의 월별 매출 집계 화면이 8~9초씩 걸렸다. 테이블 자체는 3천만 행 정도로 아주 크지는 않은데, 체감상 너무 느렸다. 우선 슬로우 쿼리 로그부터 켰다.

2. 실행계획 읽기. EXPLAIN ANALYZE 를 찍어보니 예상대로 orders 테이블에서 풀스캔이 나고 있었다. created_at 컬럼으로 범위 조건을 걸었는데 인덱스가 없었다. 인덱스 하나만 추가하면 끝날 줄 알았는데, 그렇게 간단하지 않았다.

3. 인덱스를 걸었더니. created_at 단일 컬럼 인덱스를 추가하니 풀스캔은 없어졌지만 여전히 3초가 넘게 걸렸다. 실행계획을 다시 보니 인덱스로 걸러진 행 수가 여전히 많았고, 그 다음 필터 조건(status = 'PAID')을 다시 테이블에서 하나하나 확인하고 있었다.

4. 복합 인덱스로 교체. (status, created_at) 순서의 복합 인덱스로 바꿨다. 카디널리티가 낮은 컬럼을 앞에 두는 게 항상 맞는 건 아니라는 걸 이번에 다시 배웠다 — 실제로는 쿼리가 어떤 조건을 먼저 좁히는지, 그리고 어떤 컬럼 순서로 정렬해서 커버링 인덱스를 만들 수 있는지가 더 중요했다.

5. 커버링 인덱스. SELECT 절에서 실제로 쓰는 컬럼이 몇 개 안 됐다. (status, created_at, amount, user_id) 로 인덱스를 넓혀서 쿼리가 테이블 자체를 전혀 안 건드리고 인덱스만으로 응답할 수 있게(covering index) 만들었다. 여기서 체감 속도가 확 줄었다 — 3초에서 400ms 대로.

6. 그래도 남은 400ms. 집계 쿼리 안에 서브쿼리로 사용자당 최근 주문을 가져오는 부분이 있었는데, 이게 N+1 처럼 각 사용자마다 따로 실행되고 있었다. 윈도우 함수(ROW_NUMBER() OVER (...))로 바꿔서 한 번의 스캔으로 해결했다.

7. 캐시 워밍업 문제. 인덱스를 다 정리했는데도 첫 요청은 여전히 느렸다. 버퍼 풀에 해당 인덱스 페이지가 아직 올라오지 않아서였다. 배치로 미리 워밍업 쿼리를 돌려두는 것도 고려했지만, 트래픽 패턴상 굳이 필요 없다고 판단해서 보류했다.

8. 파티셔닝은 안 썼다. 처음엔 월별 파티셔닝까지 고려했는데, 지금 데이터 규모에서는 인덱스 정리만으로 충분히 목표(1초 이내)를 달성했다. 미리 복잡하게 만들지 않고, 필요해지면 그때 다시 보기로 했다.

9. 옵티마이저 힌트는 최후의 수단. 중간에 FORCE INDEX 를 써서 강제로 특정 인덱스를 타게 만들어볼까 하다가, 데이터 분포가 바뀌면 오히려 발목을 잡을 수 있어서 포기했다. 옵티마이저가 알아서 좋은 선택을 하도록 통계 정보를 최신으로 유지하는 쪽을 택했다.

10. ANALYZE TABLE 습관. 대량 데이터를 벌크로 넣고 나서 통계를 갱신하지 않으면 옵티마이저가 예전 분포를 기준으로 실행계획을 짠다는 걸 다시 확인했다. 배치 작업 마지막 단계에 ANALYZE TABLE 을 끼워 넣기로 했다.

11. 읽기 복제본으로 분리. 이 리포트 쿼리 자체는 실시간성이 중요하지 않아서, 아예 읽기 복제본(read replica)으로 쿼리를 돌리는 것도 검토했다. 지금 당장은 과한 것 같아서 다음 스프린트로 미뤘다.

12. 모니터링 추가. 슬로우 쿼리가 다시 생기면 바로 알 수 있도록 임계치를 넘는 쿼리에 알림을 걸어뒀다. 튜닝은 한 번 하고 끝나는 게 아니라 데이터가 늘어나면서 계속 다시 봐야 하는 일이라는 걸 체감했다.

13. 정리. 오늘 배운 걸 요약하면: 실행계획을 먼저 읽을 것, 인덱스 컬럼 순서는 쿼리의 필터·정렬 패턴에 맞출 것, 가능하면 커버링 인덱스를 노려볼 것, 그리고 힌트로 억지로 강제하기보다는 옵티마이저가 좋은 판단을 할 수 있는 조건(최신 통계)을 만들어줄 것.

다음에 볼 것. 읽기 복제본 분리, 그리고 이번 기회에 미뤄둔 파티셔닝 전략도 데이터가 더 커지기 전에 한 번 정리해보고 싶다.
